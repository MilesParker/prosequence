# Session: the collection agent

Working record for the task "build an agent responsible for collecting the
information needed to populate a corpus and controlling ingestors for it".
Entries written as decisions are made. Incorporate into SESSION_FEED and delete.

Run shape asked for: `(corpus name, thesis statement, optional scope text)`.
End goal: an initial corpus with a broad range of views.

---

## Decided — not covered

### D1. The collection agent is an agent, not a Role

**Decision.** `CollectionAgent` holds no `Session`, no `capability`, and never
calls `commit()`. Its whole effect on the corpus is mediated by ingestion runs,
each of which opens its own session and commits once.

**Reason.** `Session` binds head at construction and dies on its single commit.
A collection run spans many commits, so it cannot hold one. And `capability` is
defined over `plan.Op` — session write types — which the collection agent never
produces. Giving it a session would mean either a session that outlives its
commit or a second write path; both contradict Runtime.

**Rejected.** Subclassing `Role` and overriding `_execute` to skip the commit.
That leaves `capability`, `build_plan` and `session` as inherited attributes that
mean nothing for this agent, and makes "every Role commits" — the sentence
`Role._execute`'s salvage block is written against — false.

**Consequence.** `role.py` was split. `agent.py` now holds the model loop
(graph, conditional edge, iteration cap, truncation check, tool binding, forced
finding call); `role.py` holds `Role(Agent)` — session, capability, plan, the
apply/commit boundary and salvage. `IngestionRole` is unchanged. This is the
first time the `tools` edge in that graph is exercised: ingestion binds no
interaction tools, the collection agent binds four.

### D2. SESSION_FEED has no term for this. Calling it a role would be wrong.

SESSION_FEED's "Agent Roles" section defines a role by two class attributes
(`capability`, `objective`) and by answering a disagreement with its own commit.
The collection agent has neither attribute and writes no commit of its own. The
nearest existing term is *deployment* — "the object naming which roles run at
what multiplicity" — and that is close: this is a model-driven deployment of the
ingestion role over one corpus. SESSION_FEED says nothing about a deployment
being an agent rather than a config. Recorded as new ground, not a conflict.

### D3. Document text never enters the collection agent's context

**Decision.** Fetching and ingesting are one tool call (`ingest_sources`). What
returns to the collection agent is a per-source *outcome* — fetched/skipped/
failed, extracted length, and on success the corpus delta (claims added,
inferences added, tags, commit sha). Never the extracted text, never an excerpt.

**Reason.** Staging Stage 2 keeps the fetch out of the ingestion loop because "a
fetch tool inside the loop gives untrusted document content a path to arbitrary
egress". The collection agent has exactly such a path: its `search` tool sends
free text to a third-party provider. Keeping page text out of its context is
what stops that path from being a pipe. Provenance is also unaffected: the url
is still copied by the harness from the ledger, never generated by a model.

**Rejected.** A separate `fetch` tool returning a bounded head of the text so the
agent can reject a paywall stub before spending an ingestion run. It buys a
cheap reject at the cost of putting attacker-controlled text in the context of
the one agent with an egress channel. The cheap reject is recovered
deterministically instead — see D4.

**Accepted residue.** Search results *are* page-derived and do reach the
context — but only title, host, and the provider's snippet where it has one.
The full url is withheld too (`Source.render`), because a url in the agent's
context is a url it could put in a search phrase. Titles and snippets are
provider-produced summaries rather than document content, they are what the
agent must see to select at all, and the same is true of the tags an ingestion
run returns. Named rather than pretended away.

### D4. The unusable-source gate is deterministic, not a model judgment

**Decision.** `ingest_sources` fetches, then drops a source *in the harness*
before any model sees it when extraction yields fewer than
`MIN_DOCUMENT_CHARS` (1200) characters. The agent is told the source was
skipped and why, and its length.

**Reason.** This is the paywall stub / nav page / cookie wall case, and it is
a length fact, not a reading judgment. Deciding it in the harness removes the
motive for showing the agent any text (D3) and costs nothing.

### D5. Fetching is parallel; ingestion is serialized

**Decision.** Within one `ingest_sources` call the harness fetches every
selected source concurrently (thread pool, `FETCH_WORKERS = 6`), then runs
ingestion one source at a time, in ledger order.

**Reason.** Concurrent ingestion is incorrect twice over under Runtime:

- `Session.__init__` binds head and `commit` passes that as `parent_sha`; the
  store raises `HeadMoved` when it is not current head. Two ingestion runs
  started from one head means the second commit is refused, and `HeadMoved` is
  terminal with no retry anywhere in the write path.
- Even if it committed, the second run's model reasoned over a corpus missing
  the first run's claims, so every overlap between the two documents lands
  twice. Ingestion's whole attachment premise is that the corpus in front of it
  is current.

Fetching has neither problem: it is deterministic harness I/O with no store
contact, and it is where most of the wall clock in a source batch sits when the
sources are slow servers rather than long documents.

**Rejected.** Running the ingestion *model calls* in parallel and serializing
only the commits. It fixes `HeadMoved` and not the duplication, and duplication
is the failure ingestion is least able to detect.

### D6. An ingestion failure ends that ingestion run, not the collection run

**Decision.** `ingest_sources` catches the ingestion role's terminal failures
per source (`ValidationFailed`, `HeadMoved`, `WorkingTreeDirty`, `PlanError`,
`FindingShapeError`, `Unrepairable`, `TruncatedResponseError`, and fetch
errors), records the source as failed with the exception type and message, and
continues to the next source. Guard refusals (`Refused` — kill file, per-run
cap, cumulative cap) are re-raised and kill the whole collection run.

**Reason.** Failure-is-terminal is a property of a *run*: "commit happens once
at the end of a run, so there is no partial state to reconcile". A failed
ingestion run is terminal for itself — nothing committed, error corpus salvaged
under `logs/failed/` — and the next source is a different run with a different
session, not a retry of the failed one. Nothing is recovered and nothing is
reconciled, so the property holds unchanged.

The guard is the opposite case and is deliberately separated. A kill file or a
breached cap is not a fact about one source; it is the operator or the budget
saying stop, and swallowing it per-source would turn the kill file into a
speed bump.

### D7. Bounding is harness-enforced, stopping is the agent's

**Decision.** `max_searches` and `max_ingests` are run parameters checked in the
tool dispatch: past the bound the tool returns a refusal string and the agent
keeps its turn. Stopping is the agent calling `submit_collection`.

**Reason.** SESSION_FEED: "bounding is governance and is built; stopping is a
per-role feature concern". Enforcing the bounds in dispatch rather than in the
prompt is the same move `capability` makes for writes.

**Note.** A bound refusal is returned as a tool result rather than raised. A
raise would be terminal and would lose the report; the agent hitting its ingest
budget is a normal end to a collection run, and it should say so in its report.

### D8. Token accounting: one guard per run, not one per cascade

**Decision.** The collection agent gets its own `GuardedClient` (own `run_id`);
each ingestion run it dispatches gets a fresh one. All of them share one
`GuardConfig` and one token log.

**Reason.** `per_run_token_cap` is 200k. A collection cascade of ten ingests
would breach it on the third and die, so a single guard across the cascade
would make the per-run cap mean "per cascade" — a config value silently
changing meaning because a new caller appeared. Separate guards keep the
per-run cap meaning what it says; the cascade is bounded structurally by
`max_ingests`, and the rolling `cumulative_token_cap` (read from disk) still
covers every call in it. The token log's `run_id` is what stitches the cascade
back together for reporting.

### D9. Search runs in the harness; the provider is a seam

**Decision.** `search.py` declares a `SearchProvider` protocol
(`search(query, limit) -> list[SearchResult]`) with three implementations:
`GoogleCSE` (Google Custom Search JSON API — the literal ask), `AnthropicWebSearch`
(a separate, harness-owned, guarded model call with the server-side `web_search`
tool forced), and `StubProvider` for tests. `default_provider` picks Google when
`GOOGLE_API_KEY` and `GOOGLE_CSE_ID` are in the environment, otherwise
Anthropic web search.

**Reason.** Google is what was asked for and needs two credentials that are not
in this repo's `.env`. Refusing to run without them would make the whole agent
unexercisable today. The Anthropic path needs only `ANTHROPIC_API_KEY`, which is
present, and it keeps the property that matters: the search is issued by the
harness, in its own call, and no web tool is ever bound into the collection
agent's own loop. Its results carry no snippet (the API returns title, url and
page age only), which is a narrower surface than Google's, not a broken one.

**Rejected.** Binding Anthropic's server-side `web_search` directly into the
collection agent's tool list. It is one line and it destroys the seam: search
results would arrive as blocks the harness never sees, the ledger could not
assign ids, provenance would be model-generated, and `max_searches` would have
nothing to count.

**Revised after measuring it.** The search provider gets its OWN `GuardedClient`,
not the collection agent's — see D8's reasoning applied to a third kind of
sub-run. One Anthropic web search measured at ~13-14k tokens, because the server
runs the search loop internally and bills the page results as input on that
request. Ten phrases is ~140k; twelve on the agent's own guard would have spent
three quarters of its 200k per-run cap on retrieval before it reasoned about
anything. `DEFAULT_MAX_SEARCHES` is 10 for the same arithmetic. Google CSE costs
no tokens at all, so the two providers share an interface and nothing else about
their cost profile — the default has to be safe for whichever is configured, and
the configured one here is Anthropic.

### D10. What the agent reads to judge coverage

**Decision.** `corpus_state()` returns: the thesis text(s), claim/inference
counts, the count of contesting vs concluding inferences, a histogram of
attribution-source references by host, the claim tags, and the validator's GAP-6
warnings rendered as "open ends".

**Reason.** "A broad range of views" needs a coverage signal, and the honest
ones available in Python are structural. Stance is *not* available: `computeStance`
exists only in TypeScript (`src/viz/`), and there is no Python stance query
anywhere in the harness — `read_tools.py` already records that gap and declines
to fabricate one. The host histogram is the closest mechanical proxy for range
of sources, the contests/concludes split for range of positions, and GAP-6 for
where the argument stops. All are derived from code that already exists
(`validate.check`), not reimplemented.

**Named, not solved.** Domain diversity is a proxy for viewpoint diversity and
not the thing itself; ten hostile sources on one host and one friendly one on
another will read as "one host dominates". The agent is told what the histogram
is a proxy for rather than being given a number to optimise.

### D11. `RoleState` gains a `finding` slot and keeps `plan`

**Decision.** One state class for both agents. `apply` records the raw finding
into `state.finding` generically; `plan` stays and is empty for the collection
agent.

**Reason.** Two state classes means the graph builder takes the schema as a
class attribute, for two agents sharing one graph shape. The docstring's
"role-agnostic" claim is already loose (`plan` is corpus-write-specific), and
the honest fix is to say so, which the docstring now does. Revisit if a third
agent needs a genuinely different reduction.

### D12. `_fetch_text` promoted out of `run.py`

`run.py` is the harness entry for ingestion; `sources.py` needed the same
fetch. Rather than importing across entry points, `_TextExtractor` and
`_fetch_text` moved to `fetch.py` as `fetch_text`, and `run.py` imports it.
`_seed_corpus` became `seed_corpus` for the same reason — the collection entry
seeds a corpus from `(name, thesis)` exactly as `ingest()` does.

### D13. GAP-6 warnings became `Violation` records

**Decision.** `validate.check_violations` now returns `Violation` records for
warnings as well as errors. `check` still formats both into strings, byte
identical to before, so the CLI and `Session.commit` are unchanged.

**Reason.** The coverage read lists a corpus's open ends by tag, which needs the
claim id. The alternatives were parsing it back out of the warning prose —
making the wording load-bearing, which is the exact defect the `Violation` record
was introduced to fix for errors — or reimplementing GAP-6 detection in
`coverage.py`, which is the "exactly one implementation" rule broken on purpose.

Inside CLAUDE.md's grant: `validate.py` is maintained here, GAP-6 stays a
warning, and no invariant changed.

### D14. A collection run's report is written to disk, including when it dies

**Decision.** The run report goes to `logs/collection/<run_id>.json`. A run that
fails terminally writes one too, marked `partial: true`, carrying the ledger, the
tool trace and the exception, before the exception propagates.

**Reason.** A collection run makes no commit, so it has no change record — the
place SESSION_FEED puts an agent's account of what it did. Without a file its
reasoning dies with the process, and that reasoning is the run's only output
besides the corpus itself.

The partial case was added after measuring a live run: 112k agent tokens in ten
iterations against a 200k per-run cap. Both bounds that can stop this agent
mid-conversation lose the model's report — the token cap raises, and the
iteration cap routes to apply where the last message is a tool call rather than
a finding, so `FindingCallError`. Neither should be softened; they are the
bounds working. But by the time either fires, several ingestion runs have
committed real work, and the harness's own record of what happened survives even
though the model's judgment about it does not. Same posture as `salvage`, which
writes a failed ingestion's graph out before letting the exception through.

### D15. What the live runs changed

Two full live runs (real search, real fetch, real ingestion, against a throwaway
copy of the corpus repo). Recorded because both changes are corrections to
decisions above, not new ground.

**Run 1** — 4 searches, 3 ingests. Produced 25 claims, 11 inferences, and **zero
contesting inferences**. Every opposition source the agent picked failed to
fetch (cato.org served an Incapsula bot wall as a 200 with 950 bytes; mta.info
403'd; an assembly.ny.gov page came in under the character floor), and the agent
moved on to the next position rather than naming another source for the same
one. It reported the imbalance accurately, which is the one thing that went
right.

**Diagnosis.** The fetch layer, not search or selection, is the binding
constraint on breadth — and it is not a random filter. The sites most likely to
block a plain HTTP client are not evenly distributed across positions, so
treating a failed fetch as an absent position drops whole camps.

**Change.** A section in the prompt saying so: a fetch failure is evidence about
the server, not about the position; roughly half of what you name will fail;
only a successful ingestion spends ingest budget, so name more sources per
position than you need and replace a failed one rather than moving on.

**Run 2** — 5 searches, 6 ingests, same thesis, corrected prompt. 108 claims, 79
inferences, 64 concludes, **15 contests**, 6 distinct hosts, thesis directly
concluded by 14 and contested by 10. Nine positions named, nine covered, with a
specific and honest gap list. Fetch failure rate 5 of 11, matching the prompt's
"roughly half".

**Not changed.** The fetch layer itself. Getting past a bot wall means a headless
browser, which is a different piece of work and a much larger dependency; the
prompt change recovers most of the loss for none of that.

### D16. The token log records server-tool request counts

**Decision.** `guarded_client` reads `usage.server_tool_use` and writes
`{"web_search_requests": n}` into the log line when a call used one. Omitted
entirely otherwise, so the line shape is unchanged for an ordinary model call.
`server_tool_requests(path)` totals them for reporting.

**Reason.** A web search is billed **$10 per 1,000 searches, on top of** the
tokens its results add to the context (Anthropic's web search tool docs). The
log recorded only tokens, so a spend figure computed from it was short by a
term it could not see — and the guard's whole cost story is "counts in the log,
prices applied retrospectively". Recording the count is that rule; it was just
missing a count. Found while answering "does this cost money", after ten
searches had already been billed and not logged.

**Not in the pre-flight projection.** The caps are token caps and stay token
caps. The structural bound on searches is the calling agent's own budget
(`DEFAULT_MAX_SEARCHES`), the same way `max_ingests` bounds the ingestion
cascade. Putting a per-request charge into a token projection would need a price
table in the pre-flight path, which is the one thing `guard_config` forbids by
name.

**Measured.** The whole of this task's live work — two collection runs plus a
smoke test, 54 calls — came to ~297k input / 43k output on Sonnet 5 (~$1.02)
plus 10 searches ($0.10). The search half was the invisible one.

### D17. Pages are fetched through the operator's Safari, not through `requests`

**Decision.** `fetch.py` grew a `Fetcher` protocol with two transports.
`SafariFetcher` drives the operator's running Safari via AppleScript and reads
`source of tab`; `RequestsFetcher` is the old plain-HTTP path.
`default_fetcher()` picks Safari where it can be driven, HTTP otherwise.

**Reason.** The fetch layer, not search or selection, was the binding constraint
on breadth (D15). A real browser making a real request from a real session gets
pages a plain client cannot — mta.info answered `requests` with a 403 and Safari
with 5,472 chars of article.

**Safari is the default, not a fallback.** Trying HTTP first and escalating on
failure sounds cheaper and is wrong: a paywalled article answers a plain client
with a preview stub, which is a *success* as far as the transport is concerned.
The run would ingest the stub as though it were the piece and never try the
browser that could read the whole thing. Failure is not the only thing the cheap
path gets wrong.

**Rejected: `safaridriver`.** It is the sanctioned WebDriver path and it is
wrong for this. It needs `sudo safaridriver --enable`; the man page's session
rules mean one session per host, so it buys no parallelism over AppleScript; and
its sessions are isolated from the operator's browsing data, which is precisely
the property worth having. AppleScript needs no privilege escalation and no
Safari setting at all — `source of tab` is a plain scripting-dictionary
property, where reading `document.readyState` via `do JavaScript` would have
required "Allow JavaScript from Apple Events" (confirmed: that path errors
without it, `source` does not).

**Rejected: Playwright/Chrome.** It was the first recommendation and the
operator asked for Safari. AppleScript turned out to need no new Python
dependency at all, which makes the Chrome path strictly more setup for the same
result. The one thing Chrome would add is headless operation — Safari's tabs
open and close visibly while a run goes.

**Security.** The url is passed to `osascript` as `argv`, never interpolated
into the AppleScript source. Search results are attacker-influenceable and a url
containing a quote would otherwise close the string literal and run whatever
followed — `do shell script` is one `&` away. Verified with a hostile url
carrying exactly that payload; it arrived as data.

**Cost.** Serial (one browser, one tab), visible, and ~5-10s a page. Serial
matters less than it sounds because politeness wants spacing anyway — see D18.

### D18. A run does not lean on one host

**Decision.** Two bounds. `sources.MAX_PER_HOST` (3) caps the pages one
collection run takes from a single site, checked *before* the fetch so a capped
source costs no request. `fetch.HostThrottle` enforces `MIN_HOST_INTERVAL` (3s)
between hits on one host, with a lock per host so different hosts still overlap
on a parallel transport.

**Reason.** Raised by the operator, and politeness and breadth turn out to want
the same thing. A burst of six pages off one site in a minute looks like
scraping — and on the Safari path it is the operator's own browser, session and
IP making it. Independently, a corpus drawing repeatedly on one outlet is the
concentration the breadth goal exists to avoid.

**The cap counts hosts REQUESTED, not ingested.** A fetch that failed still hit
the server, so it still counts against how hard the run is leaning on that site.
A source the cap itself skipped never reached the network and does not count.

**Reported to the agent, not hidden.** A capped source comes back as `skipped`
with "this run has already drawn 3 pages from <host>; find this position
somewhere else", so the agent diversifies rather than re-naming it.

### D19. A correction to D15's numbers

D15 recorded cato.org's Incapsula wall as a property of the site. Re-measuring
during the fetcher work, `requests` retrieved the full article from the same url
that had previously returned a 950-byte challenge page. **The wall is
intermittent.**

That is worse for the plain client rather than better: an intermittent refusal
cannot be predicted, retried around, or reasoned about from a failure log, and it
means a run's breadth depends on which side of a coin flip each opposition
source landed. It does not change D17 — it strengthens the case for a transport
that does not get challenged in the first place.

### D20. Fetching and ingesting are capped separately

**Decision.** `MAX_FETCH_PER_CALL` (8) and `MAX_INGESTS_PER_CALL` (3), enforced
in `ingest_batch`. One `ingest_sources` call fetches everything named up to the
first cap, then ingests at most the second cap's worth of what came back
readable. A readable candidate that did not fit stays `found` with its text
cached and is reported as `fetched-not-ingested`, carrying `bound_by` to say
whether the per-call cap or the run budget held it.

**Reason — this was a live bug, not a refinement.** The prompt told the agent to
over-name because roughly half of what it names is unreadable. Under the single
`max_ingests` cap that instruction was a footgun: every named source that
happened to fetch *was* ingested, so "name five to survive the failure rate" and
"spend five ingestions" were the same act, and the only thing in the way was a
run-level total the agent could burn in one call. Raised by the operator, who
asked whether the prompt made the restraint clear enough. It did not, and the
answer was not to word it better — an instruction the model can reason its way
past is not a cap.

**The two caps must differ**, or the mechanism does nothing: the fetch cap is
generous because fetching is the cheap, speculative half, and the ingest cap is
tight because ingestion is a model call and a commit.

**Caching the surplus text** is what makes the deferral honest. Without it,
coming back for a deferred candidate re-hits the server and double-counts it
against `MAX_PER_HOST` — the agent would be punished for following the
instruction.

**Slicing moved out of the tool.** `ingest_sources` used to truncate the id list
to the remaining budget before calling `ingest_batch`, which spent a FETCH slot
on a source it then refused to ingest. The whole list goes through now and
`ingest_batch` owns both caps.

### D21. The agent is not asked to judge argument strength before reading

**Decision.** "Prefer the strongest statement of a position you can find" is
removed from the prompt. In its place: judge GENRE from title and host (press
release / news report / a source that exists to take positions), and judge
strength AFTERWARDS from the ingestion delta — six inferences means it argued,
four claims and no inferences means it reported. A position whose source came
back thin is not covered.

**Reason.** Raised by the operator: the agent sees a title, a host, and
sometimes a snippet, and never the document. Asking it for a judgment it has no
evidence for does not get a cautious answer, it gets a confabulated one — and a
confident wrong call about which source states a position best is exactly the
error the instruction was written to prevent. Genre is inferable from what it
actually sees; strength is inferable from what actually landed.

This also gives the post-hoc check something to do. The delta was already
described as the feedback loop; nothing had told the agent to *act* on a thin
one.

### D22. Reaching a named publication, and the pattern behind D21

**Decision.** Naming a publication in a search phrase is framed as a *retrieval*
move with two grounded triggers — the `citation_sources` histogram shows the run
has leaned on one place, or the agent expects a kind of outlet to hold a
position and wants to find out — and explicitly not as a judgment about which
outlet argues a position best. A guess may drive a SEARCH; it may never be
recorded as coverage. Only an ingestion covers a position.

**Reason.** Operator observation that major outlets often do not surface on a
generic phrase, so a camp can look absent when it was merely outranked. This has
a consequence for D17: the value of fetching through a logged-in browser is
bounded by whether subscription sources are ever *named*.

**The first version of this entry was itself the defect D21 removes.** It said
"put the publication's name in the phrase when a position is best argued there"
— which asks the agent to know which outlet argues a position best, from a
title, having read nothing. Same shape as "prefer the strongest statement",
written into the fix for it. Caught by the operator.

**The pattern, stated once so it is checkable.** An instruction is defective
here when it requires a judgment the agent cannot ground in what it actually
receives. The distinction that makes an expectation legitimate is what it is
used FOR: a guess about the world is a fine way to *generate a query* (the
result checks it immediately, and a wrong guess costs one phrase), and is never
a basis for *recording a conclusion*. "Write the phrase the way someone holding
the position would write it" survives on exactly that test; "prefer the
strongest statement" and "where a position is best argued" do not.

**A full audit of the prompt against that test** found one further instance —
see D23. Everything else held: the position-naming and camp-vocabulary
instructions are generative guesses checked by results, and "is this asymmetry a
fact about the debate or an artifact of where I searched" is answerable from the
agent's own trace of what it searched for.

**Not built.** Domain-scoped search (`site:` on Google, `allowed_domains` on the
Anthropic tool) would make this mechanical rather than hopeful. It adds tool
surface for a benefit that has not been shown to bind, so it is recorded, not
done.

### D23. The agent is given dates, having been asked to check them

**Decision.** `SearchResult` and `Source` carry `published` — the provider's own
date string, verbatim and unparsed. Anthropic's web search supplies `page_age`;
Google's CSE carries an ISO timestamp in `pagemap` metatags on most article
pages. Rendered to the agent when present.

**Reason.** Found by the D22 audit. The prompt said "check that a source is from
the period the thesis is about" while the agent received title, host and snippet
and no date anywhere — an instruction with no evidence behind it, which is the
D21/D22 defect in its purest form. This one was fixable in code rather than
prose: both providers were returning dates that the harness was discarding.

**Unparsed on purpose.** It is shown to a model, not compared, and a wrong parse
is worse than no date. The prompt now also says what to do when there is none —
"you do not know; say so rather than assuming it is current" — because absence
is the common case and silently treating it as current is the failure it would
otherwise cause.
### D24. Arguments are selected by what is UNANSWERED

**Decision.** `corpus_coverage` returns `claim_tags` (no uuids) as the picture
of what is there, plus two renderings a tag cannot carry: `arguments_on_thesis`
— every inference targeting a thesis, the run's scoreboard — and
`arguments_unanswered`, every inference concluding a claim nothing contests.
What is already in dispute is reported as `claims_in_dispute`, a count and
nothing more.

**Reason.** Raised by the operator asking how the collection agent could know
anything about the shape of the debate. It could not: it received a flat list of
claim tags, the graph's nodes with every edge deleted. It could see that a
corpus contained "Death toll inconsistent with genocidal intent" and not that
this was an *attack on the thesis*, nor that nothing answered it.

**Three wrong selectors preceded this one, and the sequence is the record.**

1. *Depth 2.* Arbitrary, and expensive per round.
2. *Depth 1*, to save 2.6k chars a round — and then D25 removed the per-round
   cost that justified the cut, leaving a decision standing after its own
   argument had gone. Caught by the operator.
3. *Dispute* — every inference caught up in a live fight, wherever it sat. This
   fixed depth's real defect, which was measurable: **26 of the 33 disputed
   inferences sit below depth 1**, at depths 3 and 4, so a shallow read hid
   nearly all of them.

**And dispute was still wrong, in the direction that matters most.** The
operator's objection: an argument in dispute is one where opposing sides are
ALREADY PRESENT. Rendering 33 of those in full while leaving the unanswered ones
as a bare tag list put the detail — and therefore the agent's attention — on
explored ground. A collection run exists to find what is missing; a read that
foregrounds existing fights biases it toward deepening them.

**So the selector is inverted.** 30 unanswered arguments and 7 on the thesis,
where the disputed 22 are now a single integer. Roughly the same cost (11.4k
first read against 11.9k), pointed at the opposite thing.

**Why the rendering, and not the tag list it replaces.** An unanswered argument
shows what is asserted, on what grounds, under which assumptions — three attack
surfaces, which is what a search for the opposing view is actually built from.
"Bartov: Officials called for annihilation, assuming public statements evidence
specific intent" says what to search against; the bare claim it concludes does
not. `unopposed` is gone as a separate field: every unopposed claim is by
definition concluded by something, so it appears as the `to` of an unanswered
argument with its reasoning attached instead of naked.

**`unopposed` survived an objection it turned out not to have.** The operator
expected it to be full of irrelevancies. Measured: 27 entries, **zero**
attributive — because I5 forbids concluding an attributive claim, so a
source-report can never enter the concluded set. The invariant does the
filtering; no code here needs to. (Also worth separating: leaf nodes — claims
nothing concludes — are `open_ends`/GAP-6, a different set.)

**Rejected: a diff.** The operator's phrase was "squirting across an entire diff
every round", which was worth checking — no diff was ever sent.
`summarize_report` returns counts, tags and a sha. The waste was shape and
repetition, not volume.

**The prompt states the consequence the selector cannot.** An unanswered
argument is not evidence that nobody disagrees; it is evidence that the run has
not yet brought in anyone who does.

### D25. Every part of the coverage read deltas, not just the tags

**Decision.** A read takes the previous `CoverageMark` and returns only what
changed. Always re-sent: the scoreboard — counts and the per-thesis
concludes/contests split, a few hundred bytes.

**Reason, and a correction to this entry's first version.** That version
deltafied the claim tags alone and said of the rest: "they are small, they change
shape rather than grow." The operator called that superlinear, and it was:
arguments, unopposed, hosts and open ends came to 5,763 chars **re-sent every
round** — 23,052 across four reads, nearly all identical to the read before.
Full message history goes out on every call, so anything unchanged is
duplication compounding on every subsequent turn.

Measured across four reads on an 81-claim corpus: 38,304 chars for the original
flat-tag shape, 28,452 for the tags-only delta, **13,988 now** — 11,372 for the
first read and ~872 for a steady-state one, and the first read now carries 30
unanswered arguments plus 7 on the thesis where the original carried none. The
delta is what makes it affordable to pay properly for context once.

**`answered_since` is the non-obvious part.** A purely additive delta hides the
one transition that matters most: a claim LEAVING the unopposed set means a
source the run brought in answered it. That is the run's own progress, and
without it the agent can only see what it has added, never what it has closed.

**The `note` field is load-bearing.** A delta with no explanation reads as a
shrinking corpus. It says explicitly that anything unlisted is unchanged and
still above in the conversation, and `claim_tags_total` gives the real size.

### D26. Thesis connectivity is on the coverage read

**Decision.** `claims_connected_to_thesis` — how many claims are reachable from
a thesis by any chain of inference — is in the always-sent scoreboard, and the
prompt tells the agent to check it against `claims` every time.

**Reason, and how it was found.** The operator objected that this module was
being calibrated entirely against `gaza`, which is the least representative
corpus there is: hand-built as a two-source paired extraction and then
*iteratively refined for cross-source confrontation*. Measuring across all five
corpora instead turned up something much worse than a mis-tuned constant.

**`china-ai-2` has 1 of 52 claims connected to its thesis.** An ingestion run
produced 51 claims and 23 inferences forming a graph with no connection to the
question the corpus exists to argue. `china-ai` (45/45) and every hand-built
corpus are fine, so this is not a modelling limit — it is something that
happened on one ingestion run.

**Why it needed a signal rather than just a bug report.** Every other number in
the coverage read looked healthy on that corpus: 52 claims, 21 unanswered
arguments, a sensible host histogram. `concluded_by: 0` reads like an early run
rather than a broken one. A collection agent would have kept buying sources into
a corpus that could never argue its thesis, and its report would have said the
run went fine.

**Not repaired here.** The defect is in ingestion or in what it was given, and
diagnosing it means reading that run, which is separate work. Reported: see R5.

### D27. A tag is reported once, not twice

**Decision.** `ingest_sources` advances the `CoverageMark` with the tags its
results carry, so the next `corpus_state` does not list them again as new.

**Reason.** Raised by the operator asking where claims from the last ingestion
appear. They appeared in both channels: an `ingest_sources` result lists the
tags a source contributed, and a `corpus_state` delta lists everything added
since the last read. On the common path — ingest, then read state — that is a
complete overlap, paid for on every subsequent turn.

**Both channels are kept, because each has something the other cannot.** The
ingest result attributes tags to the SOURCE that produced them, which is how the
agent learns what a source actually contained; the corpus read carries
everything added since, including from ingestions the agent has since forgotten
about. Marking the ingest's tags shown keeps both without the overlap.

### D28. A cascade has a token budget, because per-run caps do not bound one

**Decision.** `collect(run_token_budget=750_000)`. Every guard the cascade
creates is registered in one list; the tool refuses further ingestion once their
combined spend crosses it, and `ingest_batch` re-checks before each individual
run. Reported in the run report as `cascade_tokens` against `token_budget`.

**Reason.** The operator asked for the cost controls to be detailed before
authorising a live run, and detailing them found the hole. `per_run_token_cap`
(200k) bounds a GUARD. D8 gave the collection agent, the search provider, and
each ingestion run their own — for good reasons, since one shared guard would
have made "per run" silently mean "per cascade". The consequence never got
followed through: a cascade holds up to ten guards, so the ceiling was
**2,000,000 tokens**, roughly six times a measured run and $4-20 depending on
the in/out mix. Nothing between that and the 5M/24h cumulative cap, which is
shared with everything else run that day.

**Checked before each ingestion, not after.** An ingestion is the expensive
call; the point is not to make it. A source not taken is left `found` with its
text cached, exactly like the per-call cap's surplus.

**A bound, not a kill.** It refuses as a tool result carrying
`bound_by: "token-budget"`, so the agent still writes its report — the same
reasoning as D7. A run that dies at its budget with nothing to show is worse
than one that stops and says why.

**750k is twice a measured run and a quarter of the old ceiling.** Run 2 (5
searches, 6 ingests) came to ~337,000 tokens. Not derived from a dollar figure:
prices stay out of the enforcement path, per `guard_config`'s own rule.

**Not in `guard_config.toml`.** That file holds bounds that apply to every run
of everything; this is one agent's run parameter, and belongs with
`max_searches` and `max_ingests` at the call site.

### D29. A malformed finding entry prunes; it does not kill the run

**Decision.** `apply.prune_malformed_entries` drops entries in
`claims`/`inferences` that are not objects, noting each; `_check_source_types`
raises `FindingShapeError` rather than `AttributeError` when nothing survives.

**Reason — found by the live trial run, and it was the run's main defect.**
Three of nine sources died on the same
`AttributeError: 'str' object has no attribute 'get'`, from
`_check_source_types` reading `c.get("attribution")` of an entry the model had
emitted as a bare string. The API enforces which tool is called and never the
shape of its arguments, so a declared array of objects can arrive holding a
string — the claim's text where the claim should be.

Wrong twice over. It escaped as an `AttributeError`, which is past every
salvage call site, so the whole finding was lost with no error corpus written.
And it was fatal where it need not be: one malformed entry among fifty is a
broken entry, not a broken finding.

**Same precedent as `prune_bad_schemes` and `prune_unresolvable`**: prune the
entry, note it, leave the systemic case to raise. An inference left citing a
dropped claim's key is picked up downstream by `prune_unresolvable`.

**It cost the trial its strongest pro-thesis sources.** City Journal
(pro-buildout) and IEA (technocratic) both died this way, and the corpus came
out with the thesis contested by 16 inferences and concluded by 1. The agent
diagnosed this itself, correctly, in its own gap list: "Two ingestion attempts
failed on tool errors (not fetch failures)". The imbalance is substantially
ours, not the world's.

First live end-to-end collection run through the Safari transport.

**Parameters.** `ai-buildout`, thesis "The AI build-out is worth what it's
costing us", scope naming power/water/land/rates/jobs/extraction/culture/siting/
who-decides and stating that participants fight over what counts as a cost.

arguing the US-China race framing is a manufactured pretext to suppress

## Deferred, with the trigger

### F1. A `find` tool, so the agent pulls rather than being pushed a digest

**Raised by the operator and explicitly held for a later iteration:** give the
collection agent its own query over the graph, so it can say "there is a gap
here, let me look at what the arguments actually are" instead of reasoning from
whatever `corpus_state` decided to include.

**It is the right shape, and most of it already exists.** `roles/read_tools.py`
is a built, tested, read-only tool surface over the session — `get_all_tags`,
`get`, `neighborhood`, `concludes`, `contesting`, `grounds_citing`,
`warrants_citing` — and **nothing currently binds it**. Ingestion is single-shot
and does not traverse; the collection agent is the first agent in the harness
whose work is shaped like traversal. SESSION_FEED already argues for this shape
("read tools are model-called and include their own entry points... whole-corpus-
in-prompt was rejected for roles whose work IS traversal, because it makes the
traversal unobservable, and traversal is what strategy consists of").

**What it would change.** `corpus_state` becomes an entry point rather than a
digest: counts, the thesis balance, and `unopposed` as the map, with the agent
pulling the arguments around whatever it wants to examine. The selector in D24
stops being a guess about what matters and becomes a default. It also makes the
agent's reasoning observable — which claims it looked at is a record of its
strategy, where today only its searches are.

**What it costs.** Every read tool is a model turn, and turns are the collection
agent's scarcest resource against the per-run token cap (measured: 112k tokens
in 10 iterations against a 200k cap). A digest is one turn; a traversal is
several. This is why it is worth doing deliberately rather than as a bolt-on —
the tool surface has to be shaped so a useful pull is one call, not five.

**Trigger:** the next time a run's report says it could not tell whether a
position was uncovered or merely not visible in what it was shown.

Not obviously worth changing, and the reason is specific to this use. Dynamic

direct call, full results — but its only benefit here is not being pinned to an
old version, and confirming it still returns the same block shape costs a live
search. Left alone pending that decision.

transport plus the 3s host throttle feel across a real 6-source batch, and
